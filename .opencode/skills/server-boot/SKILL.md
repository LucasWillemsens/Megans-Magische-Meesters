# Server Boot

Two WSL user-level processes front every paintedpillars.com URL — Caddy
on port **8080** and the cloudflared tunnel — and neither survives a
PC/WSL restart: there are no systemd units and nothing auto-starts them,
they run as manual `nohup` background processes. A reboot leaves the
deployment managers and their recorded state healthy while the public
URLs go dead behind Cloudflare 530s, and the backend server processes die
with the host. Boot the two services when the user asks to bring the site
back up or while handling their report that it is down — never as a side
effect of other work.

## Preconditions

- WSL is running and you are in the `lucas` account — the services are
  user-level and start only manually.
- The configs exist: `/home/lucas/.config/caddy/Caddyfile` and
  `/home/lucas/.cloudflared/config.yml`.
- `/home/lucas/MMM/repo/var/deployments/routes.caddy` exists — Caddy
  imports it, and it is generated by `pr_environments.py sync`. A missing
  file is an unusual state to report to the user, not a reboot symptom.

## Diagnose what is down

```
ps aux | grep -E '[c]addy|[c]loudflared'
```

Read the public symptom together with that process list:

- **Cloudflare 530** — the tunnel/proxy layer is down: cloudflared is
  missing from the list, usually caddy with it. Boot what is missing.
- **502** — the proxy chain is up but the backend Django server behind it
  is not running (any response from port 8080 means caddy is up; a 502
  through it means the backend is down). Re-run the backend's manager —
  see the boundary below — never re-boot or "fix" the proxy for a 502.
- The process list decides what gets booted; the public status decides
  whether a backend re-run is also needed.
- A service that will not stay up: read its log —
  `/home/lucas/.config/caddy/caddy.log`,
  `/home/lucas/.cloudflared/tunnel.log` — for the start error.

## The two services

- **Caddy** — reverse proxy, config `/home/lucas/.config/caddy/Caddyfile`:
  globals `{ admin off; auto_https off; http_port 8080 }`, an import of
  `/home/lucas/MMM/repo/var/deployments/routes.caddy` (the per-PR routes),
  and an `http://www.paintedpillars.com` block that serves production
  statics from `var/deployments/production/staticfiles` and
  reverse-proxies `127.0.0.1:8000`.
- **cloudflared** — Cloudflare Tunnel, config
  `/home/lucas/.cloudflared/config.yml`: tunnel
  `22f2fa20-d8ee-4b09-952f-10b422e5491b`, ingress `*.paintedpillars.com`
  → `http://localhost:8080`, credentials JSON beside it in `~/.cloudflared/`.

Caddy listens on **8080, never 80**: its `http_port` is 8080 and the
tunnel targets `http://localhost:8080`. Every check goes to port 8080.

## Start commands

```
nohup caddy run --config /home/lucas/.config/caddy/Caddyfile --watch > /home/lucas/.config/caddy/caddy.log 2>&1 &
```

`--watch` makes Caddy pick up `routes.caddy` rewrites automatically, so
PR syncs never need a reload.

```
nohup cloudflared --config /home/lucas/.cloudflared/config.yml tunnel run > /home/lucas/.cloudflared/tunnel.log 2>&1 &
```

`--config` is a global flag and must come **before** the subcommand —
placed after `tunnel run`, cloudflared prints its help and exits. Start
only what the diagnosis showed as down.

## Verify before reporting success

1. **Processes.** `ps aux | grep -E '[c]addy|[c]loudflared'` shows both
   running.
2. **Through the proxy locally.**
   `curl -s -o /dev/null -w "%{http_code}" -H "Host: pr-32.paintedpillars.com" http://127.0.0.1:8080/MMM/title/`
   returns 200 — substitute the live PR host from
   `python3 scripts/pr_environments.py status`, or send
   `Host: www.paintedpillars.com` to probe the production path.
   `/home/lucas/.cloudflared/tunnel.log` shows `Registered tunnel
   connection`.
3. **Public, cache-busted.** Cloudflare caches 530 responses, so a plain
   hit can show a stale outage:
   `curl -s -o /dev/null -w "%{http_code}" "https://<env-host>/MMM/title/?cb=$(date +%s)"`
   returns 200.

## Boundary: backends are the managers' to restart

The Django servers behind the proxy also die with the reboot, and only
their managers start them — never start one by hand, and never treat a
backend outage as a proxy failure:

- **Production** — gunicorn on port 8000, started by
  `python3 scripts/production.py deploy`. A 502 on
  `https://www.paintedpillars.com/` after the boot means it is simply
  not running.
- **Per-PR environments** — `manage.py runserver` on per-PR ports,
  started by `python3 scripts/pr_environments.py sync`; an environment
  synced before the reboot has lost its process and needs a re-sync (or
  `rebuild <pr>`).

Both re-runs follow the `deployment` skill's authorization rules, and the
managers' own procedures — commands, gates, smoke tests — live in
`scripts/production.md` and `scripts/pr_environments.md`, read before
running them; this boot never restates those.
