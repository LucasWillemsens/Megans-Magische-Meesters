Add stable name, card-type, and acquisition-date sorting controls to the player collection.

Implementation:
1. Verify the ownership relationship before coding. `viewPlayer()` currently passes the first `CardOwnerHistory` as `cardOwner`, while `viewPlayer.jinja2` iterates `cardOwner.card.all()`. Use the cards currently owned by the player as the collection source (or explicitly preserve the existing one-history set if the product decision requires it), and document that choice so historical cards owned by someone else are not shown as current cards.
2. Prefer server-side sorting in `MMM/views.py` with a `sort` query parameter accepted only as `name`, `type`, or `date`. Keep the default ordering/content stable for the current data set when no parameter is supplied; invalid values fall back to that default. Use deterministic secondary keys (`title` case-insensitively, then `id`). Do not add a model/migration field.
3. For `name`, sort by the real `Card.title` (including static CSS-playing cards). For `type`, sort by numeric `cardType` in the existing lane order 0–3 (Intelligence, Speed, Visciousness/Viciousness, Resolve), then title/id. For `date`, use the relevant `CardOwnerHistory.aquiredAt` rows for the current player and sort newest acquisition first, then title/id; if multiple acquisition rows can exist for one card, use the latest relevant timestamp and document the tie rule.
4. Pass an explicit `ownedCards` collection and the active sort key to `MMM/jinja2/MMM/viewPlayer.jinja2`. Add accessible links or buttons beside the “Owned cards” heading for default/name/type/date, preserving the player URL and query string. Mark the active control with a stable visual/ARIA state and do not require JavaScript.
5. Add tests for alphabetical names, numeric type grouping, newest-first acquisition dates, static-card titles, invalid/default sorting, and no regressions to card links or challenge content. Use distinct `CardOwnerHistory.aquiredAt` fixtures so the date test proves the implementation is not merely sorting by id.

Files to create/modify:
- `MMM/views.py` — validate `request.GET["sort"]`, build the owned-card queryset/list, compute relevant acquisition timestamps, and pass sort context.
- `MMM/jinja2/MMM/viewPlayer.jinja2` — sort controls and loop over `ownedCards` instead of issuing a new unsorted relation query.
- `var/www/static/style.css` and/or `var/www/static/cards.css` — compact, responsive sort-control layout and active/focus styles.
- `MMM/tests.py` — sorting and ownership/date regression tests.
- `MMM/models.py` — no change expected; use existing `CardOwnerHistory.aquiredAt` and `Player.getCollection()` semantics unless verification exposes a model defect.

Acceptance criteria:
- [ ] Name sorting is case-insensitive alphabetical by `Card.title`, with deterministic ties.
- [ ] Type sorting groups cards in lane order Intelligence → Speed → Visciousness/Viciousness → Resolve.
- [ ] Date sorting uses the current player's relevant `CardOwnerHistory.aquiredAt` and puts newest acquisitions first, with the tie rule documented.
- [ ] Static CSS-playing cards sort by their real title, not by generated rank/suit display text.
- [ ] The no-query/default view remains visually and functionally unchanged for the existing collection.
- [ ] Sort controls work without JavaScript, retain card links, expose active/focus state, and do not disturb challenge cards.
- [ ] Ownership filtering never displays a card whose latest owner is another player.

Dependencies:
- `player-page-polish/` — shared player-page markup and challenge styles must be settled first.
- `done/core-data-model/ownership-and-collections/` — existing ownership/history semantics.
- `done/web-flow/landing-and-player-pages/` — existing collection and card-link flow.
