Create a server-side timeline data structure that records what happens during special execution as a flat, ordered list of steps. Modify specialActions(), intSpecial(), spdSpecial(), visSpecial(), resSpecial(), and shuffleBoard() to produce timeline steps instead of (or in addition to) their current side-effect execution. Flatten the spdSpecial recursion so opponent specials produce steps in the same timeline.

## Implementation

### 1. Timeline step data structure

Define a `TimelineStep` structure (a Python dataclass or a plain dict) in MMM/views.py (or a new MMM/special_timeline.py module):

```python
# Step kinds
SPECIAL_TRIGGER = "special-trigger"
CARD_EFFECT = "card-effect"
PARTICIPANT_EFFECT = "participant-effect"
SHUFFLE_BACK = "shuffle-back"

# Step shape
step = {
    "order": int,                # sequential index
    "kind": str,                 # one of the four kinds
    "banner": str,               # sentence-style message from current print() calls
    "participantId": int,        # which participant this step belongs to
    "lane": int | None,          # lane number (1-4) to highlight, or None
    "affectedCards": [           # list of card movements/effects within this step
        {
            "cardId": int,
            "sourceLane": int,
            "sourceOrdinal": int,
            "destinationLane": int,
            "destinationOrdinal": int,
            "flipFaceUp": bool,
            "trust": bool,       # true if this card gains trust (resSpecial)
        }
    ],
    "defeatedParticipantId": int | None,  # for participant-effect: who is defeated
    "fledParticipantId": int | None,      # for participant-effect: who fled
}
```

Place this in a new module `MMM/special_timeline.py` to keep views.py clean. The `build_*` functions live there.

### 2. Make special functions timeline-producing

Each special function currently prints a message and calls participant.playCard() or other mutations. Refactor so each function:

1. **Still performs the mutations** (playCard, trust, defeat, flee, shuffleBoard) — the game logic must execute exactly as today
2. **Also returns a list of TimelineStep dicts** describing what happened, in order, for the client to animate
3. Takes a `timeline` list parameter (mutable, shared) that steps are appended to, OR returns a list of steps

Key transformations:

**intSpecial(participant, count, timeline)**
- step 0: `special-trigger` with banner `"{player} enacts master plan (max {count} cards)"`, lane = 1 (Intelligence)
- step 1..N: `card-effect` for each card that flies from hand to lane. Group all cards into one step for parallel animation, or one step per card for sequential. Recommendation: single `card-effect` step with all affected cards listed, played as a staggered wave.

**spdSpecial(participant, speed, power, opponentId, timeline)**
- step 0: `special-trigger` with banner `"{player} rushes down {opponent}"` or `"{player} flees from {opponent} and steals a card"` or `"{player} fails to flee from {opponent}"`, lane = 2 (Speed)
- If rush down: append opponent's special steps to the SAME timeline (flatten recursion) by calling opponent's special functions with the same `timeline` argument — do not nest or recurse into a new timeline.
- If flee: add a `participant-effect` step for the fleeing participant.
- If fail: just the trigger step (no card effects).

**visSpecial(participant, viciousness, opponentId, timeline)**
- step 0: `special-trigger` with banner based on outcome (win/lose/drain), lane = 3 (Viciousness)
- step 1: `card-effect` for the trusted resolve card glowing
- If opponent defeated: `participant-effect` step showing opponent board dims
- If participiant defeated (drain): `participant-effect` step showing their own board dims

**resSpecial(participant, count, timeline)**
- step 0: `special-trigger` with banner `"{player} holds and trusts up to {count} cards"`, lane = 4 (Resolve)
- step 1..N: `card-effect` steps for trusted cards gaining glow/trust lock

**shuffleBoard(participant) timeline step**
- Produces a single `shuffle-back` step listing all cards that return to the deck (untrusted face-up board cards + hand cards)
- The step's affectedCards list describes where each card came from (lane/hand) and that they all go to the deck

`specialActions(participant, timeline)` now calls each special function with the shared timeline list. Priority logic unchanged. Each special appends its steps.

### 5. Flattening spdSpecial recursion

When spdSpecial calls `specialActions(opponent)` (the "rush down" path), it passes the **same** timeline list. The opponent's special steps are appended to the same flat timeline. Example:

```
Timeline for Player A's rush down:
  step 0: special-trigger "A rushes down B" (lane=2)
  step 1: special-trigger "B enacts master plan" (lane=1, opponent's intSpecial)
  step 2: card-effect (B's cards fly to lanes)
  step 3: special-trigger "B holds and trusts" (lane=4, opponent's resSpecial)
  step 4: card-effect (B's cards glow trust)
  step 5: shuffle-back (all A's untrusted cards return to deck)
```

No nesting, no depth cap. The client just sees a flat list of steps, with banner/highlight moving to the enemy board for steps with different participantId.

### 6. Step ordering rules

Within each special function, steps are appended in chronological order:
1. `special-trigger` first (banner + "why" highlight)
2. `card-effect` steps for card movements/effects ("what" happens)
3. `participant-effect` if a participant is defeated or flees

Across specials (when multiple trigger), the order is: int -> spd -> vis -> res (same as current priority). If spd rushes down an opponent, the opponent's int -> res specials insert into the timeline before the shuffle-back of the original participant.
