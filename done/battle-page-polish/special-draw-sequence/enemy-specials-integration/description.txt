Integrate bot specials into the same timeline pipeline so enemy special sequences animate identically to player special sequences. The enemy-phase GET in viewBoard() calls _run_bot_turn(), which must now produce timeline steps for bot specials just like boardAction does for player specials.

## Implementation

### 1. _run_bot_turn: produce timeline for bot specials

Currently, `_run_bot_turn()` (MMM/views.py:598-648) draws a card for the bot, and if the bot's deck is empty after drawing, calls `specialActions(bot_participant)` and `bot_participant.shuffleBoard()` directly — with no timeline recording.

Modify `_run_bot_turn()` to build a timeline the same way `boardAction()` does for players:

```python
def _run_bot_turn(game, human_player_id):
    bot_participants = game.history.participants.exclude(player_id=human_player_id).filter(computerControlled=True)
    bot_actions = []
    for bot_participant in bot_participants:
        # ... existing draw/play logic (unchanged) ...
        
        # If deck emptied after draw:
        if bot_participant.getNextDeckCard() is None:
            timeline = []
            specialActions(bot_participant, timeline)  # modified to accept timeline
            shuffle_steps = build_shuffle_step(bot_participant)
            timeline.extend(shuffle_steps)
            bot_participant.shuffleBoard()
            # Attach timeline to response so viewBoard can render it
            bot_actions.append({
                # ... existing draw action ...
                "_timeline": timeline,   # hidden from actionPlays, handled separately
            })
        # ...
    return bot_actions
```

The timeline needs to travel from `_run_bot_turn()` through `viewBoard()` into the template context. The cleanest approach is a separate return channel:

**Option A (recommended):** Return `(bot_actions, bot_timelines)` from `_run_bot_turn()` where `bot_timelines` is a list of timelines (one per bot). `viewBoard()` appends all timelines into context.

```python
# In viewBoard():
bot_actions, bot_timelines = _run_bot_turn(game, player_id)
# ... action_plays merge ...
# Merge bot timelines:
all_timelines = (action_extra.get("timelineSteps", []) if action_extra else [])
for tl in bot_timelines:
    all_timelines.extend(tl)
context["timelineSteps"] = all_timelines
```

### 2. Enemy-phase render: timeline in context

The enemy-phase GET already renders with the correct `turn_phase="enemy"`. The timelineSteps data, when present in context, will be rendered by the template as the hidden JSON script tag (from client-sequencer-pipeline subgoal).

The JS sequencer already handles the enemy phase: when `#timelineSteps` exists and phase is "enemy", the enemy-phase flow should:
1. Show "Enemy's turn" marker (existing behavior)
2. If there are loading cards (bot draws/plays), animate them (existing behavior)
3. If timelineSteps exists, play the timeline after the loading animations

The enemy phase may have BOTH loading cards (draw) AND a timeline (special). The sequencer must handle this mixed case.

### 3. Mixed loading + timeline in enemy phase

The enemy phase can have:
- A bot draw card (loading) + no special: existing enemy animation path plays
- A bot draw card (loading) + special timeline: play the draw animation first, then the timeline
- Just a timeline (bot played no card but drew last card): play the timeline directly

Implementation in `playTimeline()`:
```javascript
if (phase === 'enemy') {
    // First, play existing loading animations (draw/play cards)
    playerElements.forEach(animateElement);
    // Wait for draw animation to finish
    const drawDuration = playerElements.length * perElementWindow + moveDuration * 1000;
    // Then play the timeline
    setTimeout(() => {
        if (hasTimeline) {
            this.playTimeline(timeline, delay);
        } else {
            reloadToBoard();
        }
    }, drawDuration + 200);
}
```

For bot specials that fire on an enemy draw (the bot draws the last card from its own deck):
- The draw animation plays first (card from enemy deck to enemy hand)
- The timeline plays after (trigger banner, effects, shuffle-back on enemy board)
- The entire sequence is on the enemy's side of the board

### 4. Enemy board targeting in sequencer

All timeline steps have a `participantId`. In the sequencer, each step must determine which board to target:
- If `participantId` matches the current player: target player's board
- If `participantId` matches an enemy: target that enemy's board

The JS already has `playerId` from the context (available via data attributes or the player's name). The enemy boards have `<h2>` with the participant's player name. A mapping can be built at initialization:

```javascript
buildParticipantMap() {
    // Get current player ID from data attribute (add if not present)
    this.playerId = parseInt(document.getElementById('playerId')?.dataset.playerId);
    // Map participant names to board elements
    this.enemyBoards = Array.from(document.querySelectorAll('.enemyBoard'));
    // For each board, the participant name is in <h2>
}
```

### 5. Bot specials: no banner conflict

When a bot special triggers during the enemy phase:
- The banner shows the bot's name in the message (e.g., "Bot enacts master plan (max 3 cards)")
- The banner appears over the bot's board area (or center-screen, but visually distinct)
- Lane highlighting targets the bot's lanes
- Shuffle-back sweeps the bot's untrusted cards back to the enemy deck
- The enemy deck wiggles

This is naturally handled by the existing sequencer since step data includes the correct participantId and banner text.

### 6. Edge: multiple bot participants

If there are multiple bot participants (future multiplayer), each bot gets its own turn in sequence. The timeline steps from each bot are concatenated in order (bot 1's steps, then bot 2's steps). The sequencer plays them sequentially. This is naturally handled if `_run_bot_turn()` processes bots in order and collects timelines in order.
