Remove the action-URL board veil again and defer the enemy turn calculation: 'end turn' renders only the player's own moves, and the bot moves are computed in the board GET that renders the enemy phase (after the browser has left the action URL), passed straight into that render via the server-side actionPlays mechanism instead of bot action cookies.

User direction (verbatim):
"obfuscate board should be removed again. It is not the preferred way to go in the end. The better solution would be to make sure that the enemy player moves aren't immediately calculated when the end turn button is pressed, but only after the board is redirected away from the action url."

Why this replaces the veil: the veil (done/battle-page-polish/implement-draw-card-animation/action-url-board-veil) was added because the end_turn POST already mutated the enemy board (bots ran on the POST), so the playerMoves render showed a board state the animations had not played out yet. Once the bots only run in the enemy-phase GET, the POST render reflects nothing but the player's own moves - which the player made themselves - and the enemy phase render marks exactly the moved enemy cards .loading. Nothing is left that needs obfuscation, so the veil goes away entirely.

Target request-by-request flow:
1. POST /game/<id>/board/<pid>/action/ action=end_turn: playcards() consumes the staged player cookies, current_participant.resetTurn(), NO _run_bot_turn(), NO bot action cookies, NO roundNumber change; renders viewBoard(turn_phase="playerMoves", clear_cookies=True) with nextUrl = board URL and sets TURN_PHASE_COOKIE="enemy" exactly as today.
2. GET /game/<id>/board/<pid>/ carrying turn_phase="enemy": viewBoard() resolves the phase from the cookie, runs _run_bot_turn() once (wrapped in try/except so a bot failure degrades to an error message, never a 500 on a plain GET), increments game.roundNumber, computes finished AFTER the bot run (bot specialActions can defeat/flee participants), builds the boards, marks the recorded bot actions loading through the existing actionPlays path, renders the enemy phase (nextUrl = /result/ when finished), and hands off "player" - or deletes the phase cookie when the game finished (game-over chain unchanged).
3. GET /game/<id>/board/<pid>/ carrying turn_phase="player": the "Your turn" marker, phase cookie deleted - unchanged.
4. Plain GET on a finished game with nothing left to play out: redirect to /result/ - unchanged deferred-result flow.

Idempotency argument: the phase cookie is single-use. The same response that runs the bots overwrites the cookie ("player") or deletes it (finished), so no refresh, back-button re-request or repeated GET can ever carry "enemy" twice; the bots run exactly once per end_turn. The bot-cookie transport disappears entirely, so there is no cross-request bot state left to double-consume either.

roundNumber decision: the increment moves from the end_turn POST to the enemy-phase GET, right after _run_bot_turn() - the round is only complete once every participant (bots included) has acted, and the single-use phase cookie guarantees the increment happens exactly once. (roundNumber is display-only: viewBoard.jinja2:24, viewGame.jinja2:56-58; no game logic keys on it.)
