The end-turn button is focused when the player phase starts, but the focused button can end up off-screen because the deckHand `scrollIntoView` race-conditions with the focus call.

## Behavior

- After end turn → enemy phase → reload → player phase, the end-turn button is focused and visible in the viewport on a 1920×1080 monitor.
- On the first paint of a fresh game, the browser's `autofocus` brings the button into view once; the JS does not double-scroll.
- When leftover `.loading` animations are still playing (e.g. just after a draw flight), the deckHand `scrollIntoView` still runs so the deck→hand flight is measured while the deck is on screen.

## Code locations

- `var/www/static/loadingAnimations.js` — the `if (phase === 'player')` branch.
- `MMM/jinja2/MMM/battle/viewBoard.jinja2` — the end-turn button has `autofocus` on first paint (unchanged).

## Implementation notes

- Two race conditions exist today: (1) `requestAnimationFrame` focus fires before the smooth `scrollIntoView` on `.playerScreen .deckHand` completes; (2) on first paint the Jinja `autofocus` lands first, then the JS smooth scroll moves the button out.
- Switch the focus call to `endTurnBtn.focus({ preventScroll: true })`.
- Gate the deckHand `scrollIntoView` and the focus call on `animationsElements.length > 0` (proxy for "previous animation happened"). On first paint, trust the browser's autofocus.
- Drop `behavior: 'smooth'` from the `scrollIntoView` so the scroll completes synchronously; the rAF focus callback can then rely on the final scroll position.

## Acceptance criteria

- Player phase after a prior animation: button focused, visible in viewport on 1920×1080.
- First paint of a fresh game: button focused via `autofocus`, visible, no double-scroll.
- After a draw: deckHand `scrollIntoView` still runs while the deck→hand flight plays.

## Dependencies

- None. Pure JS fix; no model, migration, template or CSS changes.
