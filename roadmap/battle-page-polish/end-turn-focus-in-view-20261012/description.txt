BUG: the end-turn button is focused when the player phase starts, but the
focused button is not in view.

This is a small, surgical fix in `loadingAnimations.js`. The
just-shipped player-phase branch is:

  if (phase === 'player') {
      turnMarker(delay, 'Your turn', this._scheduler);
      animationsElements.forEach((element) => element.classList.remove('loading'));
      const deckHand = document.querySelector('.playerScreen .deckHand');
      if (deckHand) {
          deckHand.scrollIntoView({ behavior: 'smooth', block: 'end' });
      }
      const endTurnBtn = document.querySelector(
          '.playerScreen .deckHand .end-turn'
      );
      if (endTurnBtn && typeof endTurnBtn.focus === 'function') {
          requestAnimationFrame(() => {
              endTurnBtn.focus({ preventScroll: false });
          });
      }
      return;
  }

Two race conditions make the focused button fall off-screen.

1. The `requestAnimationFrame` focus fires before the smooth
   scrollIntoView on `.playerScreen .deckHand` completes. Smooth
   scroll in Chrome can take ~300ms; the rAF callback runs in ~16ms
   and calls `focus({ preventScroll: false })`. The browser starts
   a *second* scroll to bring the focused element into view, and
   that second scroll races with the in-flight smooth scroll, parking
   the button off-screen.

2. On the first paint of a fresh player turn (no prior animation),
   the Jinja template's `autofocus` attribute on the end-turn button
   (viewBoard.jinja2 line 364) lands the focus correctly, but the
   smooth scrollIntoView on the deckHand then runs *after* the
   browser's autofocus, moving the button out of the viewport.

Implementation (one-file change in `var/www/static/loadingAnimations.js`):

1. Drop the deckHand-level smooth scrollIntoView when the focus target
   is the end-turn button. Replace the two-line

       const deckHand = document.querySelector('.playerScreen .deckHand');
       if (deckHand) {
           deckHand.scrollIntoView({ behavior: 'smooth', block: 'end' });
       }

   with a guarded scrollIntoView that only runs when the
   `animationsElements` array is non-empty (i.e. some animation is
   actually still finishing) AND only when the end-turn button is
   not the focus target. Practically:

       const hasAnimations = animationsElements.length > 0;
       const deckHand = document.querySelector('.playerScreen .deckHand');
       if (hasAnimations && deckHand) {
           // Bring the deck/hand into view only when there are leftover
           // .loading animations to play; otherwise let the end-turn
           // button's own scroll-into-view drive the scroll.
           deckHand.scrollIntoView({ block: 'end' });
       }

   (Switch from `behavior: 'smooth'` to the default `'auto'` so the
   scroll completes synchronously in the same task and the rAF focus
   callback can rely on the final scroll position.)

2. Switch the focus call to `endTurnBtn.focus({ preventScroll: true })`
   so the browser does not try to re-scroll. The button is then
   positioned purely by the deckHand scrollIntoView above (or by
   the browser's autofocus on first paint). Concretely:

       if (endTurnBtn && typeof endTurnBtn.focus === 'function') {
           requestAnimationFrame(() => {
               endTurnBtn.focus({ preventScroll: true });
           });
       }

3. On first paint, trust the browser's autofocus; only override
   after a player-phase animation. The trigger for the rAF focus
   call must be `hasAnimations`. Move the focus call inside the
   `if (hasAnimations)` branch, or guard it with `if (hasAnimations)`:

       if (endTurnBtn && typeof endTurnBtn.focus === 'function' && hasAnimations) {
           requestAnimationFrame(() => {
               endTurnBtn.focus({ preventScroll: true });
           });
       }

   On the no-animation branch (first paint of a fresh player turn)
   the browser's `autofocus` attribute on the end-turn button
   (viewBoard.jinja2 line 364) handles the focus and the browser
   scrolls the button into view once. We do not double-scroll.

4. Remove any `scroll-margin` CSS rules on the end-turn button. There
   are currently none in the codebase (search confirms no
   `scroll-margin` in `var/www/static/*.css`), so this is a no-op
   cleanup, but verify and document it.

5. The `turnMarker(delay, 'Your turn', this._scheduler)` call stays;
   it is the "Your turn" banner and is independent of focus.

Notes / risks:
- The `animationsElements.length > 0` gate is what distinguishes
  "first paint of a fresh player turn" from "player turn starts
  after a previous animation just finished". The
  `phase === 'player'` branch only runs when the viewBoard render
  has no `.loading` markers (the markers are stripped at line 314
  via `animationsElements.forEach((element) =>
  element.classList.remove('loading'))`), so by the time we reach
  the focus call, `animationsElements.length` is exactly the
  number of markers that *were* on the page at render time, not
  zero. We can use this as a proxy for "previous animation
  happened" (a player-phase render that has no loading markers
  means the player was just handed the turn with no leftover
  animations to play — i.e. a fresh turn).
