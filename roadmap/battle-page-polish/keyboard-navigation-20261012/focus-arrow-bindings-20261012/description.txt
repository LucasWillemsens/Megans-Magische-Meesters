Wire `_addHoverArrow` to fire on `focusin` for: (a) a hand
card that has been played (face up or face down) — arrow
from hand card to its play hologram in the lane; (b) a
ghost of a played card that is currently selected — arrow
from the ghost to the play hologram; (c) a face-down lane
card that has been flipped — arrow from the face-down card
to its flip hologram.

`_addHoverArrow` already works as-is (the source
description confirms this). The new `KeyboardSelectionControl`
(from `keyboard-selection-control-refactor-20261012/`)
emits `focusin`/`focusout` events on the right elements;
this subdirectory fills in the `_addHoverArrow` calls at
those hook points.

Background:

`_addHoverArrow(sourceEl, targetEl)` (line 1350 in the
current `cardDragDrop.js`) takes two elements and creates
a curved SVG arrow from `sourceEl` to `targetEl`, with
mouseenter/mouseleave and focusin/focusout listeners on
both. It is already used in two places:

- `_stagePlay` (line 1280) — for play holograms (hand
  card → play hologram in the lane).
- `onFaceDownCardClick` (line 1496) — for flip holograms
  (face-down lane card → face-up flip hologram in the
  holoRow).

The refactor in
`keyboard-selection-control-refactor-20261012/` adds
`onFocusIn(card)` and `onFocusOut(card)` stub methods on
the new `KeyboardSelectionControl`. This subdirectory
fills in those stubs.

User decision captured in the source description:

- `_addHoverArrow` already works as-is; the new
  selection control just hooks into it on
  focusin/focusout.

Implementation:

1. `var/www/static/cardDragDrop.js` — fill in the
   `onFocusIn` and `onFocusOut` stubs on
   `KeyboardSelectionControl`.

   In the refactor subdirectory, the stubs are:

       onFocusIn(card) { /* show arrow from card → state.hologram */ }
       onFocusOut(card) { /* hide arrow */ }

   Replace with:

       onFocusIn(card) {
           if (!card) return;
           const target = this._focusArrowTarget(card);
           if (target && this._focusArrowSource(card, target)) {
               this._showFocusArrow(card, target);
           }
       }

       onFocusOut(card) {
           if (!card) return;
           this._hideFocusArrow(card);
       }

   `_focusArrowTarget(card)` returns the target element
   for the arrow based on the card's role:

   - If `card` is a hand card with `stagedLane` set (i.e.
     the player has played it via the keyboard selection
     control), look up the keyboard-staged hologram in
     `ul.lanes li.lane.${laneName} .hologram.keyboard-staged`
     and return it.
   - If `card` is a hand card that is a ghost (the
     hand-card slot is ghosted because the player played
     the card by drag), the source is the ghost and the
     target is the staged play hologram in the lane. Look
     up via `hologram.dataset.stagedForCardId === card.dataset.cardId`.
   - If `card` is a face-down lane card with
     `dataset.stagedFlipped === 'true'` (i.e. the player
     has flipped it), the source is the face-down lane
     card and the target is the flip hologram in the
     holoRow. Look up via
     `lane.querySelector('.hologram')` (the flip
     hologram is the only `.hologram` in the holoRow
     when the flip cookie is set).
   - Otherwise return null (no arrow).

   The `_focusArrowSource` is the card itself (passed
   in). The implementation may need to return a
   different source for the ghost case: the ghost is
   the hand card with `class="ghost"`, which is what
   `card` already is. So the source and the focused
   element are the same.

   `_showFocusArrow(source, target)` and
   `_hideFocusArrow(source)` are thin wrappers around
   the existing `_addHoverArrow` flow. The simplest
   implementation reuses the existing SVG arrow
   creation:

       _showFocusArrow(source, target) {
           this._focusArrow = this._addHoverArrow(source, target);
       }
       _hideFocusArrow(source) {
           if (this._focusArrow) {
               this._focusArrow.remove?.();
               this._focusArrow = null;
           }
       }

   The `_addHoverArrow` function already binds
   `focusin`/`focusout` on both elements, so calling
   it from `onFocusIn` may produce a double-bind
   (once from the original stage-time binding, once
   from the focus-driven binding). To avoid double
   arrows, the focus-driven path uses a different
   helper that does NOT add its own focus listeners
   and just creates the SVG:

       _createFocusArrow(sourceEl, targetEl) {
           // Mirror of `_createCurvedArrow` but without
           // the focusin/focusout binding (the binding
           // is now driven by the control's
           // onFocusIn/onFocusOut).
           const svg = this._createCurvedArrow(sourceEl, targetEl);
           return svg;
       }

   Alternatively, accept the double-bind: the
   `_addHoverArrow` `focusin` listener is idempotent
   (it checks `arrow.parentNode` and creates only if
   needed) and the `focusout` listener uses a 100ms
   timeout to debounce. Double-binding is harmless.

2. `var/www/static/cardDragDrop.js` — the new control
   needs a back-reference to `CardDragDropSystem` for
   `_createCurvedArrow`. Pass it through the
   constructor:

       class KeyboardSelectionControl {
           constructor({
               ...,
               createCurvedArrow,  // (source, target) => svg
               showFocusArrow,     // (source, target) => void
               hideFocusArrow,     // (source) => void
           } = {}) {
               ...,
               this.createCurvedArrow = createCurvedArrow;
               this.showFocusArrow = showFocusArrow;
               this.hideFocusArrow = hideFocusArrow;
           }
       }

   In `CardDragDropSystem.init()`, wire:

       this.keyboardSelectionControl = new KeyboardSelectionControl({
           ...,
           showFocusArrow: (source, target) =>
               this._addHoverArrow(source, target),
           hideFocusArrow: (source) => {
               // `_addHoverArrow` already manages the SVG's
               // lifecycle via focusin/focusout. The
               // control's onFocusOut is best-effort;
               // it just makes sure no stale arrow
               // remains.
           },
       });

   The control's onFocusOut can be a no-op (the
   `_addHoverArrow` `focusout` listener already
   removes the SVG). The control's onFocusIn
   triggers `_addHoverArrow` on the source-target
   pair.

3. `var/www/static/cardDragDrop.js` — bind the
   `focusin`/`focusout` events on the right elements
   so the control's `onFocusIn` / `onFocusOut` actually
   fire. The current `cardDragDrop.js` has many places
   that focus cards (e.g.
   `selectKeyboardCard` calls
   `card.focus({ preventScroll: true })` at line 956,
   1030, 1188, etc.). Each of these is a natural
   trigger for the new `onFocusIn`. The simplest wiring
   is delegation: in `CardDragDropSystem.init()`, add
   `focusin` and `focusout` listeners on the
   `playerScreen`:

       this.playerScreen.addEventListener('focusin', (event) => {
           const card = event.target.closest(
               '.playerScreen .deckHand .hand-fan li.cardContainer, ' +
               '.playerBoard .lane li.cardContainer, ' +
               '.hologram li.cardContainer'
           );
           if (card) this.keyboardSelectionControl.onFocusIn(card);
       }, true);
       this.playerScreen.addEventListener('focusout', (event) => {
           const card = event.target.closest(
               '.playerScreen .deckHand .hand-fan li.cardContainer, ' +
               '.playerBoard .lane li.cardContainer, ' +
               '.hologram li.cardContainer'
           );
           if (card) this.keyboardSelectionControl.onFocusOut(card);
       }, true);

   The `true` (capture phase) is important: focus
   events do not bubble, so the listener must be in
   the capture phase to catch them on the right
   element.

Notes / risks:
- The delegation `focusin`/`focusout` listeners on
  `playerScreen` use the capture phase because focus
  events do not bubble. This is the standard pattern
  for delegated focus handling.
- The `focusout` event fires *before* the focus moves
  to the next element, so the arrow may briefly
  disappear and reappear when the player tabs between
  cards. The existing `_addHoverArrow` `focusout`
  listener has a 100ms debounce that masks this. The
  control's `onFocusOut` should also debounce, or it
  can be a no-op (the existing `_addHoverArrow`
  listener handles removal).
- The new control's `onFocusIn` is called for every
  focusin inside the playerScreen, including on
  non-card elements (e.g. the end-turn button). The
  `_focusArrowTarget` helper returns null for
  non-card elements, so the call is a no-op for those.
