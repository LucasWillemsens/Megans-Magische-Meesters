Add a new integer field `focusedHandCard` (default 1) on
`BattleParticipant` that remembers the 1-based ordinal of the
last hand card the player focused, across turns and page
reloads. Expose the value to the board template as a data
attribute on `#turnLimits` so the JS can restore focus to the
correct slot when the player navigates back to the hand.

This is the backend half of the broader keyboard navigation
goal. It depends on no other subdirectory; the JS routing
subgoal (`arrow-key-routing-20261012`) consumes the new field.

Background:

The existing turn-allowance data block (viewBoard.jinja2
lines 11-24) is the canonical server-to-client handoff for
per-turn state. It carries `data-draws-left`,
`data-plays-left`, `data-flips-left`, plus the raw ingredients
(`int_count`, `spd_count`, `tactics`, `drawn`, `played`,
`flipped`) and three tooltip strings. The same block is the
natural place to add a `data-focused-hand-card` attribute.

1. `MMM/models.py` — add the new field to `BattleParticipant`.

   Around line 131 (after `flippedCardsAmount`):

       # Last hand card the player focused via the keyboard
       # selection. 1-based; defaults to 1 (first hand card).
       # Persisted across turns and page reloads so the player
       # returns to the same card after end-turn / reload.
       focusedHandCard = models.IntegerField(default=1)

   Add a one-line docstring explaining the field. Do not add
   reset logic in `resetTurn()` (line 380) — the field is
   intentionally not reset on end-turn so the focus
   "remembers" across turns, only across page reloads if the
   player explicitly changes it.

   Do NOT add a `max_length`, validators, or choices; the
   value is a simple 1-based ordinal.

3. `MMM/models.py` — extend `getTurnAllowances()` (line 351)
   to include the focused hand card so the template can read
   it via the same data block.

   Add a single new key to the returned dict (just before

       "focused_hand_card": self.focusedHandCard,

   The JS will read it as

4. `MMM/views.py` — accept the focused hand card from the
   next action POST and save it.

   In `boardAction` (line 399), after the existing
   `action = request.POST.get("action", "")` read, also
   read the focused hand card ordinal from the POST (if
   present) and save it. The JS will submit a hidden input
   named `focused_hand_card` (1-based ordinal, or empty
   string if no change).

       focused_hand_card = request.POST.get("focused_hand_card", "").strip()
       if focused_hand_card.isdigit():
           ordinal = int(focused_hand_card)
           if 1 <= ordinal <= 9 * 9 * 9 * 9:  # match _noZeroOrdinal cap
               current_participant.focusedHandCard = ordinal
               current_participant.save(update_fields=["focusedHandCard"])

   The cap matches the existing `_noZeroOrdinal` cap in
   `cardDragDrop.js` line 609-617 (no-zero base-9 encoding,
   so the maximum safe integer is in the millions; the
   9*9*9*9 = 6561 cap is conservative for the realistic
   hand size of up to a few hundred cards; the cap is
   mostly defensive).

   Apply the same logic to `viewBoard` if necessary. Most
   reads are GETs and do not need to write; only
   `boardAction` writes the field.

5. `MMM/jinja2/MMM/battle/viewBoard.jinja2` — add the new
   data attribute on `#turnLimits` (line 11-24) and add the
   hidden input on the end-turn form so the value round-trips
   on the next action POST.

   a. Add `data-focused-hand-card="{{ turnAllowances.focused_hand_card }}"`
      to the existing `#turnLimits` div (around line 22,
      right after the blocked_titles block).

   b. Add a hidden input to the end-turn form (around
      line 361-367):

          <input type="hidden" name="focused_hand_card" id="focusedHandCardInput" value="{{ turnAllowances.focused_hand_card }}">

      The JS keeps this hidden input in sync with the
      currently-focused hand card slot as the player
      navigates. The submit-on-end-turn form action then
      carries the value to the server, which saves it.

   c. Optionally add the same hidden input to the draw
      form (line 294-298) so a draw action also persists

      form is sufficient because every turn ends with
      end-turn, and the player can navigate to the hand at
      any time.

6. `var/www/static/cardDragDrop.js` — keep the hidden input
   in sync with the currently-focused hand card. This is the
   minimum-viable JS to make the persistence round-trip; the
   richer "navigate back to last-focused hand card" behavior
   lives in `arrow-key-routing-20261012/`.

   In the new `KeyboardSelectionControl` (see
   `keyboard-selection-control-refactor-20261012/`), every
   time `selectKeyboardCard(card, digitBuffer)` is called
   for a hand card, also update the hidden input:

       const input = document.getElementById('focusedHandCardInput');
       if (input && digitBuffer) input.value = digitBuffer;

   The `digitBuffer` is the 1-based ordinal string that
   `_noZeroOrdinal` parses. Using `digitBuffer` (rather than
   the resolved integer) preserves any multi-digit
   selection the player typed.

   If `cardDragDrop.js` is rewritten before the new control
   is in place, this update can be done in the existing
   `selectKeyboardCard` method (line 1004) as a one-liner
   inside the new `KeyboardSelectionControl` during the
   refactor subdirectory.

Notes / risks:
- The field is intentionally not reset by
  `BattleParticipant.resetTurn()`. The user said
  "remembered across turns" — so the field persists
  across `end_turn`. If a future requirement is
  "reset the focus on end_turn", the reset belongs in
  `resetTurn` and the documentation here should be
  updated.
- The cap on the POSTed value (1 to 9^4 = 6561) is
  defensive; the existing `_noZeroOrdinal` in
  `cardDragDrop.js` allows arbitrary multi-digit
  selection, so the real upper bound is the hand size.
  The view rejects out-of-range values silently (no
  error message); this matches the existing "stale
  cookie" tolerance in `playcards` (views.py line 465)
  which silently drops unrecognized cookies.
- The end-turn form is the natural anchor for the
  hidden input because every turn ends with an
  end-turn POST. If a player navigates to a hand card
  mid-turn and then draws (instead of ending the turn),
  the new value is also persisted if the draw form
  carries the same hidden input. Either choice is
  fine; landing this subdirectory with just the
  end-turn form is sufficient and matches the
  description's "remembered across turns" requirement.
