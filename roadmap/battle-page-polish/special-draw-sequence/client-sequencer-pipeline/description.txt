Transport the server-built timeline to the client and implement a step-by-step sequencer in JavaScript that plays each timeline step sequentially, waiting for animations to finish before advancing to the next step.

## Implementation

### 1. Template: render timeline steps as hidden JSON data

In `MMM/jinja2/MMM/battle/viewBoard.jinja2`, add a hidden data block when timeline steps are present, near the existing `#turnPhase` and `#boardNext` elements:

```jinja2
{% if timelineSteps %}
<script id="timelineSteps" type="application/json">{{ timelineSteps | tojson | safe }}</script>
{% endif %}
```

Django's Jinja2 `|tojson` filter serializes the step list to JSON. The `|safe` prevents auto-escaping.

Alternative: use a `<div id="timelineSteps" data-steps="{{ ... }}" hidden>` pattern if script tags cause issues. Prefer the JSON script tag.

The timeline must survive the `_addLoadingAnimations` pipeline unchanged (it is read-only data, not card state).

### 3. JS: read timeline data in loadingAnimations.js

In `loadingAnimations.js`, add a new method `AnimateTimeline()` that fires when timeline steps are present instead of the existing batch animation logic. The `init()` / `Animate()` method should detect the `#timelineSteps` element:

```javascript

    const timelineElement = document.getElementById('timelineSteps');
    if (timelineElement) {
        const timeline = JSON.parse(timelineElement.textContent);
        this.playTimeline(timeline, delay);
        return;
```

### 4. JS: playTimeline() sequencer

```javascript
playTimeline(timeline, delay) {
    const totalTimeline = delay * 5;           // fixed total budget
    const stepBudget = totalTimeline / Math.max(timeline.length, 1);
    let cursor = 0;                            // cumulative time

    timeline.forEach((step, index) => {
        const stepDuration = this.computeStepDuration(step, stepBudget, timeline.length);
        setTimeout(() => {
            this.playStep(step, stepDuration);
        }, cursor);
        cursor += stepDuration;
    });

    // After all steps complete, reload to nextUrl
    setTimeout(() => {
        const nextUrl = document.getElementById('boardNext')?.dataset.nextUrl ?? '';
        window.location.href = nextUrl || window.location.pathname.replace('/action/', '/');
    }, cursor + 200);
}
```

### 5. JS: step type handlers

Each step kind gets its own play function:

**special-trigger:**
- Create a banner div with the step's `banner` text (reuse the existing `turnMarker()` function or create `bannerMarker()`)
- The banner appears centered, holds, then fades
- Highlight the lane indicated by `step.lane` (add CSS class `.lane-highlight` to the appropriate `.lane` element)
- If the step targets the enemy board (`participantId` differs from player), highlight the enemy's lane
- After stepDuration, remove highlight

**card-effect:**
- For each `affectedCard` in the step, animate the card using the existing `duplicateCard()` infrastructure
- Cards within the step move as a staggered wave (each card offset by a small delay, total within step budget)
- Card effects depend on flags:
  - `flipFaceUp`: card flips during flight (add `.flipFaceUp` to duplicate)
  - `trust`: card gains a glow/trust lock after landing (add CSS class `.trust-glow`)
- Use the existing `data-source-lane` / `data-source-ordinal` attributes on the card elements to fly from source to destination

**participant-effect:**
- Board dim effect: add `.board-dimmed` class to the affected participant's board area
- Banner shows the defeat/flee message
- If self-defeated (drain), dim the player's own board

**shuffle-back:**
- All `affectedCards` wave back to the deck:
  - For each card, create a duplicate flying from its current position to the deck stack
  - The deck stack is `.playerScreen .deckHand .deck` or the enemy equivalent
  - Cards fly in a staggered wave, compress timing as count grows
- After all cards arrive, add a deck shuffle wiggle animation (`.deck-shuffle` CSS class, removed after animation)
- The shuffle-back step is the last step before the phase chain continues

### 7. Integration with existing phase system

When a timeline is present, the existing phase-based animation logic (playerMoves/enemy/player branches) must be bypassed:
- The draw card animation still plays through the existing system (loading class + duplicateCard)
- After the draw animation completes, the timeline plays
- After the timeline completes, the JS reloads to nextUrl (same as today's phase chain)
- The `sequence_starting` flag on the draw action_play tells the JS that a timeline follows

To detect this in JS without a new attribute: when `#timelineSteps` exists AND the current phase is `playerMoves` (or `enemy` for bot timeline), the JS knows to first play the draw animation, then play the timeline. Implementation options:
- Option A: The timeline element's presence alone signals the sequencer mode. Existing Animate() runs first for the draw loading cards, then a second pass reads the timeline and plays it. The draw animation's reload-to-board is suppressed when timeline is present.
- Option B: Embed the timeline start as part of the loading animation flow. The last draw card gets a special `.sequence-starting` class, and the sequencer kicks in after that card's animation finishes.

Recommendation: Option A. The draw card flies (existing animateElement), then when all loading cards resolve AND `#timelineSteps` exists, start the sequencer.
