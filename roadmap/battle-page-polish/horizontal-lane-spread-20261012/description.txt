The four player lanes are too narrow: at the current 56% field width
with 14% horizontal padding on each side, only ~5 cards fit per row
in a typical lane before the lane-stacking JS adds an overflow row.
The field should be roughly 90% of the viewport width, so the same
lane comfortably fits ~9 cards per row on a 1920px monitor.

Both player fields (lanes + trustedCards rows) must stay
symmetric — the four lanes are equal width and the trustedCards
row is centred under its lane. The change widens `ul.lanes` to
~90vw with a sensible cap for very large screens, and re-tunes
`LaneCardStacking.MAX_CARDS_PER_ROW` in `laneStacking.js` so the
overflow trigger matches the new per-row capacity.

Mobile / narrow viewports are explicitly out of scope — the
existing `@media (max-width: 700px)` block (cards.css line 984) is
untouched and continues to handle small screens.

   Current values:

   New values (target ~90vw on a 1920px screen, capped at a

       padding: 0 2%;

   Reasoning:
   - `min(90vw, 1600px)` gives 90vw on viewports up to ~1778px
     wide, then caps at 1600px so the lanes do not exceed
     ~1600px total field width on a 4K display. The player
     deckHand is still anchored to the bottom of the playerScreen
     flex column, so extra horizontal space on the lanes does
     not affect vertical layout.
   - Reducing the side padding from 14% to 2% gives the four
     lanes more room. Combined with the wider field, each lane
     is now ~22% of `min(90vw, 1600px)`, which is roughly
     22% of 1728px = ~380px per lane on a 1920px monitor. That
     is enough for 9 overlapping cards at the existing
     1.4em overlap offset.
   - Tightening `gap: 2%` to `gap: 1.5%` recovers some of the
     space taken by the wider field, but the gap can be left
     at 2% if the visual result is fine. Either value is
     acceptable; prefer 1.5% for a slightly tighter field.

2. `var/www/static/laneStacking.js` — re-tune `MAX_CARDS_PER_ROW`.

   Current value (line 3):
       static MAX_CARDS_PER_ROW = 15;

   New value:
       static MAX_CARDS_PER_ROW = 25;

   The existing `reflowRowGroup()` math (line 31-53) clamps the
   effective per-row count to `Math.min(MAX_CARDS_PER_ROW,
   Math.max(1, Math.floor((laneWidth - firstCardWidth) /
   overlapPx) + 1))`. The 25 cap is a safety net so an
   extremely wide viewport (e.g. 4K) does not try to fit 50
   cards in one row and produce a single-row layout that is
   impossible to read. The nth-child offset rules in
   `cards.css` (`ul.cardRow li.cardContainer:nth-child(N) { left: ... }`)
   define explicit per-card left positions for N up to 20 (see
   `cards.css` lines 1199-1218); the existing test
   `test_lane_overflow_splits_rows_without_merging_back` (tests.py
   line 2304-2314) asserts that `MAX_CARDS_PER_ROW <= max defined
   nth-child offset` and that overflow rows use the absolute
   positioning. After raising the cap to 25, the
   `nth-child(N)` rules only need to cover up to 25. Add the
   missing rules for nth-child(21)-(25) in `cards.css`:

       .playingCards ul.cardRow li.cardContainer:nth-child(21) { left: 29.8em; z-index: 21; }
       .playingCards ul.cardRow li.cardContainer:nth-child(22) { left: 31.2em; z-index: 22; }
       .playingCards ul.cardRow li.cardContainer:nth-child(23) { left: 32.6em; z-index: 23; }
       .playingCards ul.cardRow li.cardContainer:nth-child(24) { left: 34.0em; z-index: 24; }
       .playingCards ul.cardRow li.cardContainer:nth-child(25) { left: 35.4em; z-index: 25; }

   The left-offset delta per card is 1.4em (matching the
   `overlapOffset` of 1.4 in `LaneCardStacking`), so each
   subsequent card is 1.4em to the right of the previous one.
   For nth-child(21): 20 * 1.4em = 28.0em, plus the
   `0.0em` starting offset adjustment is 28.0em; following
   the pattern of existing rules, use `29.8em` (21 * 1.4em ≈
   29.4em + 0.4em rounding). Match the existing
   `nth-child(1) { left: 0 }` baseline; the empirical pattern
   from `cards.css` (lines 1199-1218) is `left: ((N - 1) * 1.4)
   + 0` rounded, so:
       nth-child(21) → 20 * 1.4 = 28.0em  → 28.0em
       nth-child(22) → 21 * 1.4 = 29.4em  → 29.4em
       nth-child(23) → 22 * 1.4 = 30.8em  → 30.8em
       nth-child(24) → 23 * 1.4 = 32.2em  → 32.2em
       nth-child(25) → 24 * 1.4 = 33.6em  → 33.6em

   Adjust the z-index to match. The existing pattern uses
   `z-index: N` for nth-child(N) where N goes 1..20.

   Wait — the existing CSS uses a different pattern. Look at
   the actual deltas in `cards.css` lines 1199-1218:
       nth-child(1)  left: 0
       nth-child(2)  left: 3.2em
       nth-child(3)  left: 4.6em
       ...
       nth-child(20) left: 28.4em

   The deltas are: 3.2, 1.4, 1.4, 1.4, ..., 1.4. The first
   delta is 3.2em (the card width is ~3.2em including margin),
   and the rest are 1.4em (the overlap). So the formula is
   `left: 3.2em + (N - 2) * 1.4em` for N >= 2, and `left: 0`
   for N = 1.

   For N=21..25:
       nth-child(21) left: 3.2em + 19 * 1.4em = 3.2em + 26.6em = 29.8em
       nth-child(22) left: 3.2em + 20 * 1.4em = 3.2em + 28.0em = 31.2em
       nth-child(23) left: 3.2em + 21 * 1.4em = 3.2em + 29.4em = 32.6em
       nth-child(24) left: 3.2em + 22 * 1.4em = 3.2em + 30.8em = 34.0em
       nth-child(25) left: 3.2em + 23 * 1.4em = 3.2em + 32.2em = 35.4em

   So:
       .playingCards ul.cardRow li.cardContainer:nth-child(21) { left: 29.8em; z-index: 21; }
       .playingCards ul.cardRow li.cardContainer:nth-child(22) { left: 31.2em; z-index: 22; }
       .playingCards ul.cardRow li.cardContainer:nth-child(23) { left: 32.6em; z-index: 23; }
       .playingCards ul.cardRow li.cardContainer:nth-child(24) { left: 34.0em; z-index: 24; }
       .playingCards ul.cardRow li.cardContainer:nth-child(25) { left: 35.4em; z-index: 25; }
